## Reproduction

1. Start fresh loopback PostgreSQL and Redis fixtures. Set `DATABASE_URL` and `DIRECT_URL` to the same empty database, then run `pnpm db:generate`, `pnpm db:migrate` and `pnpm exec prisma migrate status --schema prisma/schema.prisma`.
2. Set `G1_TEST_DATABASE_URL` to that disposable database, with a name starting `flowdesk_g1_`, and `G1_TEST_REDIS_URL` to a dedicated Redis instance on a nondefault port. Use `127.0.0.1` for both. The suite temporarily changes Redis memory settings, so dedicate the instance to this run. Execute the opt-in Vitest command above.
3. For the upgrade test, archive `prisma/` at `541b7b8` into a temporary directory. Point both database URLs at a separate disposable database. Apply its migrations, seed synthetic tenant/customer/text rows and confirm their values after applying the new migration and checking status.
4. For smoke, use a clean fixture database or the synthetic upgrade fixture and a separate Redis database. Use the [G0 loopback and LF environment setup](../g0/baseline.md#reproduction-and-boundaries). Set `API_URL` to the dedicated local API, verify health, then run `pnpm smoke`.

Live Meta deliveries, hosted configurations, multi-replica deployment, full Redis data loss after an acknowledged classification handoff, and downstream AI/action idempotency remain unverified. Coverage measurement was outside these runs.
